# Buddy Mode (Plan 19) — Design

**Date:** 2026-08-02
**Status:** Approved in brainstorming; awaiting written-spec review.
**Depends on:** the shipped app through v0.13.0 — `backgammon_core` (rules,
legality, event-log replay), `engine_bindings` (wildbg best-move/cube advice),
the existing match setup options, History/analysis persistence, and the
Firebase telemetry stack.

## Summary

Buddy Mode turns the phone into a participant at a **real, physical
backgammon board**. The user props the phone so the rear camera covers the
board at an angle; Buddy watches the game through the camera, follows the
position and dice in real time, and speaks. The MVP mode is **opponent**:
the engine plays one side — Buddy announces its dice and moves out loud, the
user physically executes them, and Buddy verifies the placement. The user
plays their own side normally; Buddy observes their dice and moves and folds
them into the authoritative game state.

The architecture is **mode-pluggable from day one**: perception and
game-following form one shared core, and a thin *commentary policy* on top
decides what is spoken and shown. Coach and tracker modes are later policies
over the same core, not new subsystems.

## Goals

- Play a complete match against the engine on a physical board, hands-free
  on the phone except for corrections and setup.
- Perception that works across **different boards and lighting conditions** —
  no hardcoded colors, measured against a multi-board/multi-lighting corpus.
- A **readability indicator** that tells the user, specifically, why the
  board cannot be read and what to fix.
- Spoken output (TTS) for dice confirmations, Buddy's moves, objections to
  illegal moves, cube actions, and game/match results.
- Finished games recorded to History exactly like digital matches, so
  post-match analysis works unchanged.
- Degrade gracefully: every perceptual input has a manual on-screen fallback,
  so the worst case is "slightly assisted hot-seat", never a broken game.

## Non-goals (this plan)

- **Voice input** (speech commands) — later phase; the spec reserves room.
- **Coach/tracker modes** — later policies; only the seam ships now.
- **Cube perception** — the cube is tracked internally and negotiated
  verbally; the physical cube is ritual. (Likely never needed.)
- Reading a board **mid-game with no session context** ("walk up to a random
  position") — full-board reads exist only for start-of-session confirmation
  and drift recovery, always primed by an expected state.
- Desktop support. Buddy Mode is mobile-only (camera/TTS); the entry point is
  hidden on desktop like other mobile-only surfaces.

## Vocabulary

- **Session** — one Buddy match: calibration through match end.
- **Belief** — Buddy's current model of the physical board, always derived
  from the authoritative `GameState` plus any observed-but-unconfirmed diff.
- **Policy** — the mode layer deciding speech/prompts (`OpponentPolicy` now;
  `OpenCoachPolicy`, `PrivateCoachPolicy`, `SilentTrackerPolicy` later).
- **Corpus** — the committed set of real board photographs the perception
  test harness scores against.
- **State-primed query** — a perception question that carries its expected
  answer space ("which of these 7 legal plays happened?"), never an
  open-ended read.

## The central architectural bet

Because the app maintains the authoritative game state — position, whose
turn, the dice, and the full legal-move list — perception never has to read
the board from scratch during play. It answers **small discrete questions
generated by the state**:

- "Which of these N legal plays matches the observed change?"
- "Are the two settled dice showing 6 and 3?"
- "Does point 6 now hold the 4 checkers I expect?"

Matching an observed diff against a known, enumerated answer space is
drastically more tractable than unconstrained board reading, and it is what
makes the robustness goals achievable with a classical-CV backbone.

## Modes and the commentary-policy seam

```dart
/// What a mode says and shows. Receives session events; never touches
/// perception or game state directly.
abstract class BuddyPolicy {
  void onDiceRead(Player roller, Dice dice, Confidence c);
  void onPlayObserved(Player mover, Move play);
  void onIllegalPlayObserved(String reason);
  void onBuddyMoveChosen(Dice dice, Move play);      // opponent mode
  void onPlacementVerified(bool correct, String? fix);
  void onCubeAction(CubeAction action);
  void onReadability(ReadabilityState state);
  void onGameEnd(GameResult r);
  void onMatchEnd(Player winner);
}
```

`OpponentPolicy` (MVP) speaks Buddy's dice/moves, acknowledges the user's
plays tersely, objects to illegal or incomplete plays, and runs the verbal
cube negotiation. The other three policies change only which of these events
produce speech and whether engine advice is voiced for human plays.

## Opponent session flow

### Setup

Reuses the existing match-setup options: match length, cube on/off (the
settings' cubeless toggle), difficulty, and which color Buddy plays. New
Buddy-specific choices: phrasing style (terse/friendly — a setting), and the
side of the table the user sits on (needed to map board orientation).

### Calibration (once per session, repeatable on demand)

1. **Corner alignment.** A board-outline overlay on the camera preview; the
   user drags four handles to the playing field's corners (or accepts an
   auto-detected quadrilateral when detection is confident). This locks the
   homography mapping camera pixels to board coordinates.
2. **Orientation.** The user confirms which side is their home board; with
   the corner assignment this fixes the 24-point coordinate frame.
3. **Color learning.** The checkers are in the known starting position, so
   Buddy gets ~30 labeled checker samples and per-point background samples
   for free. It learns this board's two checker colors, felt, and point
   colors. **No color constants exist anywhere in the pipeline.**
4. **Confirmation.** Buddy renders its belief of the starting position over
   the preview; the user confirms. Mis-detected calibration restarts cheaply.

**Calibration is a session-long contract, continuously re-validated — not a
one-time gate.** Every stable frame throughout the session runs cheap
validity checks (corner-patch verification against the calibration's
remembered appearance, exposure statistics, gyro history) regardless of
whether a query is pending, so degraded conditions are caught the moment
they happen — a nudged board, a lamp switched off, a phone slide — not the
next time Buddy needs an answer. When a check fails: the readability light
drops immediately with the named cause, perception answers are suppressed,
and if the cause invalidates calibration (geometry moved, colors no longer
match), the session routes to the recalibration flow — the same guided
corner/confirm loop as setup, with the fast path of nudging the existing
corners. Play resumes exactly where it paused; the authoritative game state
is never touched by a readability outage.

### The user's turn

1. User rolls both dice anywhere on their visible board half.
2. Frame gating waits for stability (gyro + inter-frame diff); the mic's
   dice-transient detector, when it fires, shortens the wait by directing
   attention ("look now").
3. `readDice` runs on a stable frame → Buddy speaks confirmation
   ("You rolled 6-3."). Low confidence → readability flow or tap-to-enter
   fallback prompt.
4. User moves checkers. On the next stable frame(s), `matchLegalPlay`
   compares observed per-point occupancy deltas against the legal-play set:
   - unique match → Buddy acknowledges ("13/7, 8/5.") and folds the move;
   - ambiguous → on-screen disambiguation (tap one of the candidates);
   - matches an illegal or incomplete play → Buddy objects with the reason
     ("that leaves the 3 unplayed") and waits for the board to change;
   - no plausible match → drift-recovery path.
5. Dance (no legal moves): Buddy announces it and passes the turn, mirroring
   the digital auto-pass behavior.

### Buddy's turn

1. Buddy asks the user to roll for it. Same dice-reading path.
2. The engine picks its play (existing difficulty pipeline). Buddy speaks
   the dice and the move ("I rolled 5-2 — play 13/8, and 24/22.").
3. The user places Buddy's checkers. `verifyExpectedBoard` checks the
   resulting position against the expected one:
   - correct → brief acknowledgment, play continues;
   - wrong → Buddy names the discrepancy ("the checker from 13 should be on
     8, not 7") and re-verifies until correct. Repetition escalates to the
     on-screen belief mirror with the discrepancy highlighted.

### Cube

Cube state lives in the engine exactly as in digital play. Buddy doubles by
voice ("I double — take or drop?"); the user answers on screen (voice later).
The user doubles via an on-screen Double button (same gating rules as the
digital game, including Crawford). The physical cube is the user's ritual to
maintain; Buddy never looks at it.

### Game and match end

Announced by voice with the score; recorded through the existing
`GameController` persistence path, so History, the score sheet, and
post-match analysis all work with zero new code.

### Corrections and drift

- The screen always shows the **belief mirror**: a rendered board of Buddy's
  current belief beside/over the camera preview. Any cell can be tapped to
  correct a misread before it folds.
- Manual dice entry is always one tap away.
- Drift recovery: a full-board `verifyExpectedBoard` against the
  authoritative state; irreconcilable differences surface as an on-screen
  side-by-side ("camera says / game says") for the user to resolve — either
  fix the physical board or accept a correction to the observation.

## Perception core — `packages/board_vision`

A new **pure-Dart package**. Input: RGB frames (plain byte buffers +
dimensions) and the session's calibration; output: typed answers with
confidences. **No camera, plugin, or Flutter dependency** — the package
builds and tests on Windows against the corpus, in keeping with this repo's
"logic packages are desktop-testable" discipline. The app layer owns the
`camera` plugin and feeds frames.

- **Geometry.** Homography from calibration; each point, the bar, and both
  off trays become fixed quadrilateral ROIs in board space. Perspective
  means far-side ROIs are smaller/noisier — accuracy targets are tracked
  per-half in the harness.
- **Color model.** Two learned checker-color distributions plus per-ROI
  background models from calibration. Classification is *relative* (sample
  vs. its own ROI background), which is the lighting-robustness mechanism.
  Slow exposure drift re-normalizes on each confirmed-stable frame.
- **Occupancy and deltas.** Per-ROI checker-pixel mass → estimated count.
  Counts are never trusted in isolation mid-game; they feed diff-matching
  against the enumerated legal plays, where the expected deltas are known
  (±1/±2 per affected point, hits routing through the bar).
- **Stack verification.** Verifying "this point holds K checkers" uses the
  known checker diameter from calibration and edge periodicity along the
  stack axis — verification against an expected K, not blind counting.
- **Dice.** Locate two die-sized high-contrast square blobs in the board
  region on stable frames; read pips by blob detection within each face.
  This is the sub-problem most likely to need the ML escape hatch.
- **Stability gating.** Frames are processed only when the gyro reports the
  device still AND inter-frame difference is below threshold — perception
  runs on a handful of stable frames per turn, not on a video stream. This
  is both an accuracy and a battery/performance decision.
- **ML escape hatch (policy, staged).** If the corpus harness shows a
  sub-problem below target after honest classical effort, that sub-problem
  alone gets a micro-classifier (TFLite, trained on corpus crops). The
  escape hatch is planned, budgeted, and *scoped to the failing sub-problem*
  — never a general detector.
- **Performance.** Target ≤300 ms per state-primed query on a mid-range
  phone, computed in a worker isolate. Dart first; FFI/Rust only if
  profiling on-device proves it necessary.

### Provisional accuracy targets (the spike calibrates these)

| Query | Target | Fallback when missed in play |
|---|---|---|
| Calibration completes (guided) | ≥95% of attempts | retry with guidance |
| Dice pair read (settled, stable) | ≥98% | tap-to-enter dice |
| Legal-play identification (top-1) | ≥95%, ambiguity prompt otherwise | tap-to-pick candidate |
| Placement verification (the regions the play touches) | ≥95% per dictated turn | belief mirror + tap-correct |
| Full-board resync (vs expected) | ≥90% per region | side-by-side resolve |

Targets are per-attempt on corpus conditions (see Testing); the spike's job
is to confirm or renegotiate them with measurements before Phase 2 commits.

**Reshaped by the user at the gate follow-up, 2026-08-21.** The last two rows
used to be scored *per whole board*, and the first real corpus said that was
the wrong shape twice over. It is not the question a session asks: after Buddy
dictates a move the session knows exactly which regions the hand went to, and
`BoardDiscrepancies` already carries the answer region by region, so sweeping
the other twenty and failing on one of them measures something nobody asked.
And per whole board the numbers are arithmetic rather than promises — a resync
sweep is twenty-six regions on a folding case, so ≥90% of boards is ≥99.6% of
regions, a figure this table never argued for and no classical pipeline offers.
**Neither number moved: both are still 95% and 90%.** What moved is the
denominator — per touched-region-set per turn, and per region. The whole-board
rates are still measured and printed on every run, promised nothing.

The reshape is honest about what it is worth on its own: measured on the day it
landed, placement verification on the real corpus went from **0/6 boards to 2/6
turns** — the far-half tall-stack undercount is what the rest depends on, and
that is perception work rather than bookkeeping.

## Readability indicator

A three-state light (green/amber/red) over the preview, computed from:
board-in-frame + homography freshness, gyro stability, frame sharpness, and
lighting adequacy (dynamic range within board ROIs). It is evaluated
**continuously on every stable frame for the whole session**, not merely
when a query is pending (see the calibration section's session-long
contract). Amber/red always name the failing cause on screen — "I can't see
the left edge", "too dark", "the phone moved — re-check the corners" — and
the transition to red is spoken once (not nagged). Perception answers are
suppressed while red, and a red caused by invalidated calibration offers
the recalibration flow directly.

## Audio

- **TTS out:** `flutter_tts`, mobile-only (guarded like other mobile-only
  surfaces). Every spoken line is mirrored on screen (accessibility, and
  noisy rooms). Phrasing setting: terse ("13/8, 24/22") or friendly
  ("move one checker from 13 to 8...").
- **Mic in (MVP scope = one trick):** a dice-roll transient detector that
  directs perception's attention. It is an optimization, not a dependency —
  the mode works identically with the mic permission denied.
- **Permissions:** camera permission already ships (QR join). New:
  `RECORD_AUDIO` (Android) / `NSMicrophoneUsageDescription` (iOS), requested
  in-context the first time a Buddy session starts, deniable without loss of
  core function.

## App integration

- **`BuddySession`** orchestrates: owns calibration state, the frame/query
  scheduler, the policy, and a `GameController` wired with a
  `PerceptionHumanAgent` (the human side — moves arrive from vision or
  on-screen fallback instead of board taps) and the existing engine agent
  for Buddy's side, plus the placement-verification step.
- **Screens:** `BuddySetupScreen` (match options + side/seat), the
  calibration flow, and `BuddyGameScreen` (camera preview, belief mirror,
  readability light, spoken-line transcript, manual-entry fallbacks, and the
  Double button under digital-game gating rules).
- **Persistence:** the standard match/History pipeline; sessions are
  resumable the way local matches are (calibration re-runs on resume).
- **Analytics:** session started/completed, calibration attempts,
  per-fallback-use counters, readability-red rate — through the existing
  `AppAnalytics` seam. These numbers decide where perception effort goes
  after launch.

## Testing strategy

- **The corpus is the test suite.** A scripted capture checklist (shot with
  a normal phone camera, no app build needed): the starting position and a
  set of mid-game positions and dice throws, across **≥2 different physical
  boards, ≥3 lighting conditions (daylight/lamp/dim), and 2–3 camera
  angles/heights**, each with a small human-labeled ground-truth sidecar
  (JSON). Committed downsampled (≤1280 px, curated, target ≤25 MB total);
  originals stay out of the repo.
- **The harness runs as tests.** `board_vision`'s suite scores the pipeline
  against the corpus and asserts the accuracy-target thresholds — a
  perception regression fails CI exactly like a rules regression. Unit
  tests cover geometry math, color-model updates, diff-matching, and every
  fallback path with synthetic frames.
- **On-device reality.** CI has no camera. A manual test protocol (a short
  scripted match with checkpoints) runs on the user's devices per release,
  and the analytics counters above monitor the field.
- **Session logic** (BuddySession, policies, fallbacks) tests with a fake
  perception layer — same pattern as `MatchTransport`'s fakes.

## Phasing

- **Phase 1 — feasibility spike (the gate).** Capture corpus v1; build the
  harness + geometry/calibration + color model + occupancy/dice prototypes;
  produce real accuracy numbers. **Gate:** targets met or consciously
  renegotiated before anything else is built. If dice-reading misses badly,
  the MVP proceeds with tap-to-enter dice and the escape hatch is scheduled.
- **Phase 2 — perception core to target.** `board_vision` complete against
  the corpus, including drift recovery and stability gating.
- **Phase 3 — the mode ships.** BuddySession, OpponentPolicy, TTS,
  calibration + game screens, readability, fallbacks, persistence,
  analytics; manual on-device protocol passes; MVP releases.
- **Phase 4+ (separate future plans):** coach/tracker policies, voice input,
  micro-classifier if the escape hatch was triggered.

## Risks and honest fallbacks

| Risk | Mitigation |
|---|---|
| Dice pips too small/blurry at real distances | Mic-directed attention + settle wait; tap-to-enter dice keeps the mode shippable; scoped micro-classifier as the planned fix |
| Stack miscounts on the far board half | State-primed verification (never blind counts); per-half targets; user guidance to favor near-half seating during calibration |
| Lighting shifts mid-session | Relative color model + re-normalization; readability amber names it; recalibration is cheap |
| Phone gets bumped | Gyro flags it instantly; corner-nudge recalibration |
| Perception fundamentally misses targets in the spike | The gate exists precisely for this: renegotiate targets, reduce MVP claims (assisted mode), or stop before Phase 2 spends anything |

## Out of scope, recorded for later

Voice commands ("double", "take", correction by voice); coach modes and
their fairness options (earbud-aware private coaching); tracker-mode auto
score-keeping for two humans; cube perception; arbitrary-position pickup.
